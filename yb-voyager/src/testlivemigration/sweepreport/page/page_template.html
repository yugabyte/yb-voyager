Does assess-migration warn you?

This is the question the sweep was built to answer: before a migration starts, does the tool tell you which of your columns will not survive it? Comparing what assess-migration reports against what actually happened in live migration:

And the nine false alarms, which matter because they cost the tool's credibility and push people into schema changes they do not need: composite and its variants, point[], timetz[], vector[], xml[], tsquery. Four of those are arrays — flagged by name, and then measured migrating perfectly.

Scope: judged on live migration, which is what assess's live lists describe. Types YugabyteDB cannot store at all are excluded from both counts — no warning can help there.

Only three things go wrong

The long list of broken types comes down to three causes, and each needs a different fix.

  1. The type is on the exclusion list — the column is removed from the change stream. You get one warning line, and a question that --yes answers for you.
  2. The type is on no list and has no conversion rule — the value reaches the target in a form it cannot read, and the import or the export process dies.
  3. The type is on no list and converts wrongly — a different value lands, and nothing is logged at all.

A fourth case sits outside all three: an array of an excluded type is never matched by the guardrail, so it is never dropped — and then usually migrates perfectly, which shows the exclusion was not needed in the first place.

What's actually broken

  1. Ranges and multiranges are dropped and barely announced. The snapshot keeps the old values, so the table looks full while going stale. An update touching only a range column produces no event at all — the log sequence jumped 748 → 750. Nothing in assess-migration, analyze-schema or the docs mentions ranges.
  2. Two unhandled null pointers kill the exporter, and say nothing. An hstore containing a NULL value crashes it while serializing the row; a domain over an enum crashes it while listing the database's types, before reading anything. Both print only Export of data failed! Check logs for more details. Neither names a column, a type or a reason — and because the exporter is gone, initiate cutover then hangs forever instead of failing.
  3. Domains are invisible until they stop the migration. Every layer matches the domain's own name and never looks at what it wraps, so a domain over xml is unmentioned everywhere while bare xml is flagged.
  4. Values are pasted into SQL instead of passed as parameters. Hence column "nan" does not exist — a float value read as a column name.
  5. Unknown types are sent as hex, and the target is left to guess. The value's text form is put on the wire as raw bytes and arrives as a hex string. Every one of these is the same bug wearing a different error:
    • tid → \x2831372c3529 = (17,5) — invalid input syntax
    • regclass → \x70675f74797065 = pg_type — relation does not exist
    • regproc → \x76657273696f6e = version — function does not exist
    • regoper → \x7c2f = |/ — operator does not exist
    • regnamespace → \x7075626c6963 = public — schema does not exist
    • pg_snapshot, regconfig, regdictionary, regrole, regcollation — same shape, each naming its own hex
    These all stop the import only because their target types have strict parsers. Where the target type is text-like, the hex is accepted and stored. That is not a worry, it is measured: refcursor arrived as \x6f746865725f637572736f72 — the string other_cursor — and was stored without complaint. Same defect, no error, permanent corruption.
  6. Dates travel as integers with no range check. date 'infinity' arrives as -5877611-06-21. timestamptz travels as a string and handles the same values correctly, so the right pattern already exists in the codebase.
  7. Cutover asks a question nobody can answer. With standard input from /dev/null it panicked in 5 seconds; with an unfed pipe it waited indefinitely. Only an operator at a terminal can answer it, and by then production is on YugabyteDB.
  8. A dead migration reports as healthy. After a bad value killed import data, get data-migration-report kept returning success with stale counts for 15 minutes.
  9. A newer target gets fewer warnings. The same schema produced 25 findings against YugabyteDB 2024.2 and 19 against 2025.2. The six that vanished were the multiranges — whose columns export data still drops.
  10. The offline list is stale in both directions. pg_lsn and txid_snapshot are flagged as unsupported but migrate fine offline; xid8 is flagged nowhere and corrupts silently.

What to fix

First — stop losing data quietly

  • Carry ranges, or say so up front. The array form already migrates perfectly, which proves the text form survives the pipeline. Registering the range types for the same string passthrough is the small fix; adding them to assess-migration is the minimum.
  • --yes must stop meaning “agree to lose columns.” Dropping data should require its own flag.
  • Make “excluded” mean one thing. Excluded columns are still copied by pg_dump, so you get correct old rows and frozen new ones — harder to notice than an empty column.
  • Separate “YugabyteDB supports it” from “we can carry it.” Conflating those is what hides the multirange warning on new targets.
  • Quote and cast every value. Nothing should be concatenated into a statement because its type has no rule.
  • Guard the exporter against nulls, and make its failures name the table, column and type instead of pointing at a log directory.
  • Warn when an update diffs to nothing on a REPLICA IDENTITY FULL table. That DEBUG line is why range-only updates vanish without trace.
  • Say when the importer has died. The status report should not keep answering normally after the import has exited.

Then — close the reporting holes

  • Teach assess-migration the shapes it cannot see: ranges, domains resolved to their base type, and xid8.
  • One list, consumed by both assess and export data, resolved through typelem and typbasetype, so arrays and domains can never disagree again.
  • Make assess respect the connector actually in use; today it assumes the logical one and never mentions the gRPC-only exclusions.
  • Give analyze-schema a non-interactive path — it currently panics when there is no terminal.
  • Range-check the datetime converters, or move date and timestamp to the string path timestamptz already uses.
  • Define “skips” in the docs. It currently means three different things.

How this was measured

The type list is not hand-written. A coverage guard reads pg_type on a live server, and for every candidate attempts to declare a column of that type. Anything that can be a column and has no probe fails the build — so a new PostgreSQL version or a newly installed extension surfaces as a test failure instead of a silent gap. The only permitted exclusion is a type whose column declaration is refused, recorded with the server's own error.

Each probe is one table run through insert, update-this-column, update-a-different-column, delete, and NULL transitions. Verdicts come from comparing rows and reading the exported event stream on disk, not from the migration's own report. Every batch carries int and text control probes, and any run whose controls fail is discarded — this page will not display a verdict from such a run.

The suite is repeatable: migtests/scripts/run-datatype-sweep.sh runs it, writes a results CSV per run, and sweepreport diff compares two runs so “what changed in datatype support this release?” is a mechanical answer.

Why the control probes matter

Roughly a fifth of all runs failed identically: the snapshot finished, no events followed, nothing logged an error. It looked like an overloaded machine. In fact the change-capture engine reads the machine's Kubernetes config at startup, that file delegates to a corporate login helper, and an expired session made the helper print a coloured error. The escape characters break the YAML parser and the process aborts before reading a row.

A harness that retries and treats “failed the same way twice” as a result would have turned that into confident false findings — it briefly did, including a claim that a column containing an empty string blocks a migration. Every one was withdrawn. The lesson generalises to the product: a failure that logs nothing is indistinguishable from success. A dropped column, a stalled importer and a dead exporter all present as silence.

How much is actually measured

194 types across three modes is 582 cells. 476 of them carry a measured outcome. The rest are listed here rather than quietly rounded up.

ModeMeasuredWhat is missing
Offline194 of 194Nothing.
Live190 of 1942 never run (box3d, topology.topogeometry); 2 gave no result because the exporter crashed before reaching them (hstore holding a NULL, and a domain over an enum — both crashes are themselves findings, listed above).
Fall-back92 of 19437 not reachable because the type stops the forward migration; 49 spoiled by another type sharing the run and needing a solo re-run; 15 never run; 1 no result.

Fall-back is the weak column and the report does not pretend otherwise. It is the most expensive mode to run — every probe needs a full forward migration, a cutover and a reverse stream — and a single type that wedges the importer takes its whole batch down with it before cutover. That is why 49 cells say Not measured: those runs need re-running one type at a time.

Not attempted at all, and why

  • Fall-forward — needs a third database container, which does not fit in the available memory. No cell in this report covers it.
  • The gRPC connector — the test container does not publish the cluster's internal RPC ports. This one matters more than it sounds: the gRPC connector has a different exclusion list, dropping tsvector, hstore, citext and ltree, and assess-migration never mentions those.
  • PostGIS end to end. A PostgreSQL image with PostGIS 3.6.4 was built for this and the source side works, but YugabyteDB 2026.1 cannot install the extension, so the column cannot exist on the target — which is why those rows read Target rejects type rather than untested. vector (pgvector) is available on YugabyteDB and was tested.

Where this disagrees with the earlier audit

That audit called built-in ranges the worst case: silently missing from every event, in no list, invisible everywhere. The data loss is real and reproduced here. The mechanism is not — ranges are matched deliberately by a catalogue query and excluded on purpose, and export data does print a warning naming the columns. It also claimed ranges and tsquery deadlock cutover, which did not reproduce. Its domain-over-point finding was correct, including the struct-JSON detail.
