Does assess-migration warn you?

This is the question the sweep exists to answer: before a migration starts, does the tool tell you which columns will not survive it? We compared what assess-migration reports against what happened in live migration, type by type.

Four things go wrong

The long list of broken types comes down to four mechanisms, each needing a different fix.

  1. The column is excluded from the change stream. Voyager prints one notice at export time and --yes answers the question. The snapshot keeps the old values, so the column looks populated while going stale. Ranges get this treatment without any warning from assess-migration.
  2. A value is pasted unquoted into the UPDATE statement. INSERT and DELETE bind parameters; UPDATE builds SQL text. The word NaN becomes a column name, an XML tag becomes a syntax error.
  3. A value travels as raw bytes and lands as hex. When the change-stream connector has no name for a type, the importer turns the bytes into a \x… literal. A strict target type rejects it and the import stops. A text-like target type accepts it and stores the hex as the value, with no error at all: refcursor and domain(tsvector) are the two measured cases.
  4. A corner value is normalised away. Transaction ids come out as 0 or as a fresh id, -0.0 loses its sign, 24:00:00 becomes midnight, numeric 1.500 becomes 1.5. No error, no warning.

A fifth case sits with the target, not with voyager: YugabyteDB refuses numeric NaN, infinite intervals and the internal statistics types outright. Those eight are the only types that also fail offline.

What's actually broken

Every item below was measured on a run whose control columns passed. The companion fix queue has the values, error codes and probe ids for each.

  1. Transaction and command ids are replaced. xid and cid arrive as 0. xid8 arrives as a different 14-digit number on every run, offline and live. Only xid is on a list, and the export guardrail does not read that list.
  2. Two text types are stored as their own hex. refcursor holding other_cursor arrives as \x6f746865725f637572736f72. domain(tsvector) arrives as one lexeme containing the hex of the whole value, while bare tsvector works. Same in fall-back.
  3. Three corner values are normalised. numeric 1.500 loses its trailing zeros in every mode including offline. float8 -0.0 loses its sign and time 24:00:00 becomes 00:00:00 in live and fall-back.
  4. Ranges are dropped with no assess warning. All nine range probes: offline works, live and fall-back column dropped. Arrays of ranges work everywhere, which shows the pipeline can carry the text form.
  5. Values are pasted into SQL instead of bound. column "nan" does not exist is a float value read as a column name. XML, regtype and int2vector fail the same way, and in fall-back bare xml stops the reverse import.
  6. Unknown types are sent as hex and the target is left to guess. 44 types stop the import this way: tid arrives as \x2831372c3529, which is (17,5); regclass arrives as \x70675f74797065, which is pg_type, and is then looked up as a relation that does not exist. The ISBN family, cube, seg, the vector types and every domain over a geometric type fail the same way.
  7. Dates travel as integers with no range check. date 'infinity' arrives as -5877611-06-21 and BC dates as negative years; the import stops with time zone displacement out of range. timestamptz travels as text and handles the same values correctly, so the right pattern already exists.
  8. YugabyteDB refuses eight values outright, offline as well as live: numeric NaN and infinities, interval infinity, and the four internal statistics types. Assess-migration mentions none of them.
  9. Two values kill the exporter before any row moves. A domain over an enum, and an hstore holding a SQL NULL (fixed on main by #3711, not in this build). The only message is that export failed.
  10. Every reg* type stops the live import, and offline regconfig and regdictionary arrive with a different object id behind the same name. Whether that offline difference matters depends on whether anything compares raw ids across the two databases.

What to fix

First, stop losing data quietly

  • Do not hex-encode a value bound for a text-like column. The importer's byte converter needs the source column type, which it does not receive today. One change closes the two silent hex cases and 44 loud ones.
  • Bind UPDATE parameters the way INSERT already does. Nothing should be spliced into SQL because its type has no converter.
  • Treat xid8 and cid like xid, and make the export guardrail read the same list assess reads. These are system columns and excluding them with a warning is the right end state.
  • Carry date, timestamp, -0.0 and 24:00:00 as text through the change stream, the way timestamptz already travels.
  • Check where numeric scale is lost. Insert 1.500 directly into an unconstrained numeric column on YugabyteDB; if it keeps the zeros, the loss is voyager's.
  • Give column loss its own flag. --yes should not also mean "agree to drop these columns".
  • Make exporter deaths name the table, column and type instead of pointing at a log directory.

Then, make the warnings match the behaviour

  • Report range columns in assess-migration, using the same catalogue query the guardrail already uses to drop them.
  • Report the eight values YugabyteDB refuses, so they are found before the import instead of by it.
  • Make assess and the guardrail agree on wrappers. Either resolve arrays and domains to their inner type in both, or stop flagging the 32 wrappers that are measured working. The measurements favour the second.
  • Decide what a reg* column should mean after migration. Its value is an object id that only makes sense on the source.

How this was measured

The type list is not hand-written. A coverage guard reads pg_type on a live server, and for every candidate attempts to declare a column of that type. Anything that can be a column and has no probe fails the build — so a new PostgreSQL version or a newly installed extension surfaces as a test failure instead of a silent gap. The only permitted exclusion is a type whose column declaration is refused, recorded with the server's own error.

Each probe is one table run through insert, update-this-column, update-a-different-column, delete, and NULL transitions. Verdicts come from comparing rows and reading the exported event stream on disk, not from the migration's own report. Every batch carries int and text control probes, and any run whose controls fail is discarded — this page will not display a verdict from such a run.

The suite is repeatable: migtests/scripts/run-datatype-sweep.sh runs it, writes a results CSV per run, and sweepreport diff compares two runs so “what changed in datatype support this release?” is a mechanical answer.

Why the control probes matter

Roughly a fifth of all runs failed identically: the snapshot finished, no events followed, nothing logged an error. It looked like an overloaded machine. In fact the change-capture engine reads the machine's Kubernetes config at startup, that file delegates to a corporate login helper, and an expired session made the helper print a coloured error. The escape characters break the YAML parser and the process aborts before reading a row.

A harness that retries and treats “failed the same way twice” as a result would have turned that into confident false findings — it briefly did, including a claim that a column containing an empty string blocks a migration. Every one was withdrawn. The lesson generalises to the product: a failure that logs nothing is indistinguishable from success. A dropped column, a stalled importer and a dead exporter all present as silence.

Fall-back is the weak column and the report does not pretend otherwise. It is the most expensive mode to run — every probe needs a full forward migration, a cutover and a reverse stream — and a single type that jams the importer takes its whole batch down with it before cutover. That is why the "Not measured" column above is not zero: those runs need re-running one type at a time.

Not attempted at all, and why

  • Fall-forward — needs a third database container, which does not fit in the available memory. No cell in this report covers it.
  • The gRPC connector — the test container does not publish the cluster's internal RPC ports. This one matters more than it sounds: the gRPC connector has a different exclusion list, dropping tsvector, hstore, citext and ltree, and assess-migration never mentions those.
  • PostGIS end to end. A PostgreSQL image with PostGIS 3.6.4 was built for this and the source side works, but YugabyteDB 2026.1 cannot install the extension, so the column cannot exist on the target — which is why those rows read Target rejects type rather than untested. vector (pgvector) is available on YugabyteDB and was tested.

Where this page changed after the audit

The first version of this page called twelve live cells silent corruption: numeric and float8 NaN and infinities, BC and infinite dates, and domains over xml and point. Re-running each one alone showed a loud importer error with a SQLSTATE in every case; the harness had compared values after the importer was already dead. They are now listed as import stops. The fall-back column was also repeating the live result, because the harness kept the first mismatch it saw and the forward leg ran first. It now records the reverse leg separately, and seven fall-back cells were re-run: five corrupt in the reverse direction too, lo works, and tsquery is excluded with a prompt rather than silently lost. The full account is in the audit page linked from the fix queue.
